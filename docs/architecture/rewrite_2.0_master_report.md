## 一、结论先行（三句话）

1. **2.0 的本质决策不是"选哪个技术栈"，而是"先把 core 层从 GUI 与隐式单例中彻底解放出来，并用契约测试锁死"**。这件事（阶段 0+1）无论未来选哪条路线都必须做；做完之后，换栈成本从"凭运气重写"降为"按说明书翻译"。
2. **推荐：2.0 走 PySide6 深度重构**（阶段 1 解耦 + 阶段 2 令牌化 GUI），加权 4.13/5.00 四路线第一，且在"美观权重翻倍"的敏感度检查下仍与 WPF 打平（4.03 vs 4.05）。**保留 WPF 期权**（阶段 3），**不推荐 Tauri 与 Qt C++**。
3. **目标定位不变**：比拟 PCL2 地位的 Steam mod 包管理与下载器。视觉对标 PCL2 实测参数（白卡 245/255 + 3px 阴影 0.07→0.4 悬停抬升、90ms 颜色/150ms 高度缓动），功能对标 Steam 社区浏览 + IDM 下载体感，并部分支持接入 Steam 官方。

## 二、评估输入：理论与现实

### 2.1 理论基础

- **加权决策矩阵**（1-5 分，5 最优；权重按项目实际风险结构设定）——迁移成本与 AI 团队可维护性各 0.25：本项目最大风险不是"选错栈"而是**"重写中途烂尾"**（参见现实证据 §4.3：1.4.1 打包单轮超时 4 次的重型构建教训）。
- **Team Topologies** 对齐：域 owner 端到端 build+run+fix（用户明定规矩）——"团队全部经验在 PySide6"这条属硬约束，评估的第一性原则是**驾驭度优先于理论最优栈**。
- **Big Ball of Mud / 本质 vs 意外复杂度**：system_contracts §4 逐条拆出 10 项本质复杂度（换栈也照搬：provider 链、下载状态机、熔断、双失效缓存、steamcmd 串行锁…）与 9 项意外复杂度（巨型类、clear() 重建联想、四套去抖/代际机制混用、隐式单例群…）——**意外复杂度全部是 Python/Qt 混用方式的债，不是 Python 本身的债**。

### 2.2 现实经验（本迭代 1.4.2 的三起硬崩溃，全部是铁证）

1.4.2 修交互 bug 的过程中，一个半月内**三次复现级崩溃**被定位：

| # | 崩溃 | 根因 | 归类 |
|---|---|---|---|
| 1 | 搜索途中 SIGSEGV（exit -1073740791 + QThread destroyed while running） | `self._worker = _SearchWorker(...)`中途被覆盖 → GC 析构仍在 run() 的 C++ 线程 | **意外**（Python 引用计数 × QThread 生命周期） |
| 2 | 图片回调 RuntimeError（Internal C++ object already deleted） | 跨线程信号 Emit 到已析构 QLabel | **意外**（信号接收端生命周期） |
| 3 | 非主线程改 GUI（隐患，未被 C++ 断言抓到但实测可崩） | `w.ready.connect(lambda …)` —— **PySide6 对裸 lambda 走 DirectConnection → 槽在工作线程执行并改 status_label/completer 模型** | **意外**（连接方式） |

**这三条全部发生在 Qt 互操作层，不在 core 域，也不在任何"语言选型"能救的层面**：换 WPF/Tauri/Qt C++ 同样有等价物（WPF 的跨线程 dispatcher、Rust 的 Send/Sync、Qt C++ 的 queued connection）——**它们是"架构契约"问题，不是"语言"问题**。1.4.2 已逐条修复（保活池 + 绑定方法连接 + 回调守卫），修复模式已沉淀为 system_contracts §3 的"Qt 线程规矩七组"——**这就是契约文档作为迁移说明书的具体价值**。

相反，**core 域七迭代零回归**（87+ 套件 + 1.4.2 新增 17 项交互断言全绿）：说明真正稳的资产恰恰是与 GUI 解耦的那部分——这直接支持"先解耦、再谈换栈"的结论。

### 2.3 实测/经验数据（非估计值）

- 429 指纹研究（34 次本机实测）：steamcommunity 详情页限流由**请求头指纹**触发（裸 Chrome UA 缺 Accept-Language → 429；补 `Accept-Language: zh-CN` 或 Steam 客户端 UA → 200，各 3/3；429 响应从不带 Retry-After）。这是**可移植的协议层知识**，任何栈都照用。
- 403 分层对策、steamcmd 输出行为（无逐字节进度/0 字节假成功/downloads 临时目录）、GGNetwork 响应形状、WinSock 10053 熔断规律——同为不可移植**经验**资产（需在新栈重新发现）。
- 交付链现状：PyInstaller → Inno，45.5MB，单线 main + tag，唯一可用推送通道（schannel + 127.0.0.1:7897 代理）。
- 迭代过程教训：重型构建/回归任务不能压成员单轮（packager 连续 4 次轮次超时 → captain 接管）；成员移除后同名不可复活（平台约束，已入记忆）；QTest qWait 的 C++ 事件循环不释放 GIL，饿死纯 Python 工作线程（测试假象，不影响真实 app.exec 用户）。
- 用户需求调研窗口：Valve 2026-01-08 工坊版本控制（mod 分支/历史版本）——**功能差异化窗口可能比换栈更值得占用 2.0 周期**。

### 2.4 数量级声明（诚实边界）

冷启动/内存数值为**量级估计**（业界公开基准 + 同类工具经验值），本机未做跨栈实测。阶段 0 内附"最小原型实测"判据（§5 阶段 0 第 3 条），立项前可先测再定。

## 三、四路线 × 五维度矩阵（1-5，5 最优）

| 维度（权重） | ① C# WPF | ② Tauri（Rust+Web） | ③ Qt6 C++ | ④ PySide6 深度重构 |
|---|---|---|---|---|
| 美观上限（0.20） | **5** | **5** | 4 | 3.5 |
| 效率（0.15） | **5** | 5 | **5** | 2 |
| 迁移成本（0.25，5=最低） | 2 | 1 | 2 | **5** |
| 分发与更新（0.15） | 4 | **5** | 3 | 4 |
| AI 团队可维护性（0.25） | 4 | 3 | 3 | **5** |
| **加权总分** | **3.85** | **3.35** | **3.35** | **4.13** |

**敏感度检查**（美观权重 0.35 顶到最高）：WPF 4.05 vs PySide6 重构 4.03 —— 仍打平。WPF 只在"美观=绝对唯一目标+不惜重写"时是优选；Tauri 在任何权重组合下不占优（两项 5 分被迁移 1 + AI 维护 3 的双重短板压死）。

### 各路线一句话机制论证（详见 rewrite_feasibility §2）

- **WPF 美观 5 是机制级结论**：控件模板 + Storyboard/EasingFunction，PCL2 实测参数全在其默认能力之内；但团队零经验、零渐进路径、87+ 回归套件作废、回退=沉没成本全损。
- **Tauri 美观/分发双 5 但迁移 1**：唯一连"思维方式"都要换的路线（所有权/借用），borrow checker 把 AI 迭代速度压到最慢档。
- **Qt C++ 效率 5 但 AI 维护 3**：C++ 编译器不挡错误（bug 更隐蔽），构建链（msvc/CMake/windeployqt）对 AI 不友好。
- **PySide6 重构迁移 5**：core 前置条件已大半满足（core 已不导入 Qt）；每步在现有回归套件护栏内迭代，**唯一具备密集回退点的路线**（1.5 → 2.0 每阶段独立可交付、可停止）。 QSS 美观上限 3.5 是硬约束（无 box-shadow、无 CSS transition），但 1.4.2 令牌系统已证"明度阶梯+描边+动画插值"路线可接近 PCL2；**QML 混合（关键页面换 QQuickWidget）可把上限拉到 4.5+，2.0 可选做或不做**。

## 四、推荐路线与分阶段计划（可执行、每阶段带判据）

> 原则：每个阶段结束 = 一次可交付版本（全量回归 + 讨论组评审 + 版本号，遵守迭代四要素）。

### 阶段 0：契约固化（并 1.5 中后期，~3-5 人日）
1. system_contracts §1 每条不变量落成显式契约测试（补缺口：节流并发覆盖、terminal 语义、_cancelling 竞态时序、双失效缓存、SQLite 30s 锁、api_cache 深拷贝断言）。
2. **判据**：无 PySide6 环境跑 core 测试全绿（core 无 Qt 化可验证）。
3. 立项前可选：最小跨栈原型实测（WPF 壳调全部核心端点 + steamcmd 编排冒烟，2-3 人日）——把 §2.4 的估计值换成实测再定。

### 阶段 1：core 层解耦（2.0 阶段一，~5-8 人日）
1. 隐式单例 → 显式注入（Services 容器升级，get_config/cache/registry 收口）。
2. 回调 → 事件总线（DownloadManager 统一 append 订阅；GUI 订阅，边界唯一化）。
3. job 状态机显式化：引入 PENDING 状态吸收 `_pending_refresh`/`_pending_search_term` 隐式标志位。
4. workers 层收口：_ImageTask 逃逸点改正；后台任务管理器（保活池+代际+取消一体）从 workshop_tab 提升为 GUI 层公共组件——**1.4.2 的保生池/绑定方法连接直接平移进去**。
5. **判据**：core 包零 Qt 导入（静态检查）；契约测试全绿；GUI 行为零回归（87+ 套件 + 17 项交互断言 + 两轮独立复测）。

### 阶段 2：GUI 层按令牌重写（2.0 阶段二，~10-15 人日）
1. workshop_tab 拆分：游戏选择器组件（**联想模型化：QStandardItemModel/QCompleter 增量更新替代 clear() 重建——1.4.2 已落地验证**）/ 列表容器 / 卡片组件 / 预取管理器 / 代际管理器（去抖+代际+在途一站式，消灭四套混用机制）。
2. 设计令牌全量落地：1.4.2 已完成卡片试点 + dark/light QSS 骨架；1.5 清单（library/downloads/settings 卡片迁移、对话框阴影）；2.0 清单（左侧栏导航旗舰改动、density/动效令牌落地为 QPropertyAnimation/QVariantAnimation 封装）。
3. **判据**：tools/verify_design_shots.py 像素断言链延续；每组件独立契约测试。

### 阶段 3：期权评估（2.0 完成后，按需）
- 美观/效率仍不达预期 → WPF 移植立项（契约文档+契约测试就是移植说明书，解析器先行 → provider/状态机 → UI 最后）。
- 均达标 → 保持 PySide6 转功能迭代（Valve 2026-01-08 工坊版本控制差异化窗口可能更值）。

## 五、风险登记与回退点

| 路线 | 主要风险 | 触发信号 | 回退动作 |
|---|---|---|---|
| ④ PySide6 重构 | 拆分引入行为回归；代际管理器迁移期结果错乱 | 任何轮次回归红 | 逐 commit 回退；最差停在 1.5（可交付版本不亏损） |
| ① WPF | 烂尾（周期 > 预期 2 倍）；429 经验在新 HTTP 栈失效 | 原型无法复现关键行为（如详情页 200 率） | 立项前 2-3 日最小原型，失败即放弃 |
| ② Tauri | borrow checker 迭代慢 | 连续多轮卡同模块 | 阶段 0 原型失败即放弃 |
| ③ Qt C++ | 构建链吃轮次 | windeployqt 跑不通 | 冒烟构建链失败即放弃 |

**所有路线的公共前置：阶段 0 + 阶段 1。** 这是"④ 为默认、换栈为期权"的结构性原因：阶段 1 完成后，④ 只需继续，换栈则按说明书翻译——**先做 ④ 的阶段 1，等于给自己留了换栈的选项，但不提前下注。**

## 六、供讨论组与用户裁决的开放问题

1. **路线 ④ 为默认是否接受**（或将 WPF 提为首选——代价：~90% 代码重写、回归体系重建、一次梭哈无回退）。
2. **QML 混合架构做不做**（把 PySide6 美观上限 3.5 → 4.5+，代价是引入 QML 心智成本，2.0 阶段 2 内可选）。
3. **2.0 功能 vs 重构的资源排序**：Valve 2026-01-08 工坊版本控制（mod 分支/历史版本）是功能差异化窗口，2.0 周期内是否优先占用？
4. **自动更新**：当前无；1.5/2.0 阶段是否列入（Squirrel.Windows/自建差分，Python 生态有实现，不阻塞）。

## 七、一句话结论

**2.0 = 先解耦锁契约（阶段 0+1，任何路线的前置），再令牌化重构 GUI（阶段 2），WPF 作为期权（阶段 3）；Tauri/Qt C++ 当前不推荐。** 依据：加权矩阵（4.13 第一）+ 本会话三起硬崩溃全部落在 Qt 互操作层而非语言层 + core 域七迭代零回归证明"解耦即稳定"。决策权在用户，讨论组按三原则评审。
