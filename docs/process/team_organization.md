## 一、核心规矩（用户明定，优先级最高）

### 规矩 1：bug 归属制（反泛修复专员）

**bug 出现时，交给"开发该域的成员"修复；团队不设只修 bug 的泛修复专员。**

- **理由**：bug 多源于该域开发者自己的失误；让原作者修自己的债，才有正向反馈（自己写的债自己还，下次写出同类 bug 的概率下降）。泛修复专员会造成**交接债**（读代码成本、误伤风险）与**责任外移**（写的人不背修的 KPI）。
- **理论依据**：Team Topologies stream-aligned 原则——域 owner 端到端 **build + run + fix**，不做交接（§二团队拓扑映射）。
- **1.4.2 实证重构**：联想 / 退格 / 中英适配 / 输入反馈原本分散在多个成员手里，现合并为一个**「游戏搜索域」任务（t2）交 ux-fixer 一人端到端**——搜索 popup 的所有交互行为归一人守。同域的硬崩溃（t1，QThread 生命周期）因属稳定性专精域，由 stab-fixer 先行打底，但根因仍在游戏搜索域内，ux-fixer 是最终域 owner。
- **域 owner 名册**（现行）：

| 域 | owner | 守什么 |
|---|---|---|
| 游戏搜索 / 联想 / 输入反馈 | ux-fixer（t2） | `workshop_tab.py` 搜索框路径全部交互行为 |
| 稳定性（QThread / 对象存续） | stab-fixer（t1，并出 t3 架构契约） | 跨域线程生命周期守卫；核心逻辑文档化 |
| 视觉 / 设计令牌 / QSS | ui-designer（t4 + t7） | `styles.py` 令牌体系，被全员消费 |
| 流程 / 继任者文档 | process-doc（t5） | `docs/process/*` |
| 独立复测 | qa-indept（t6，**不写产品代码**） | 验证权 |

### 规矩 2：结构化开发纪律（用户怀疑 bug 泛滥源于此，必须成文）

1. **单模块行数上限约 800 行，超出必须拆分。**
   - 现行反例（2026-10-01 实测）：`swdm/gui/workshop_tab.py` **1749 行**（captain 点名的"意外复杂度"集中地，搜索 / 联想 / 翻页 / 空态 / 勾选全挤一个文件）· `swdm/gui/detail_dialog.py` 1222 行 · `swdm/core/downloader.py` 894 行。
   - 架构契约文档任务（t3，stab-fixer）必须把这些"意外复杂度"列为 **2.0 重构目标**，给出拆分边界提案。
2. **契约先行**：公共 API + docstring **先于实现写定**（签名 / 参数 / 返回 / 异常 / 不变式先冻结，实现后填）。契约即评审对象——讨论组与复测对着契约验，不对着实现验。
3. **用户可见功能必须同时交付 QTest 真按键交互测试。**
   - **API 层断言不算数**：直调 `setText` / 方法是 API 测试；`QTest.keyClicks` / `keyClick` / `QInputMethodEvent` 才算用户交互测试（`tests/test_user_interaction.py` 头部公约）。
   - **直接教训**：1.4.1 的 86 + 111 项复测**全是 API 层**，六方评审 6/6 零反对交付，用户一上手就撞到 4 个交互 bug（输入未识别 / 联想混乱 / 回车闪退 / 退格吞字符）——1.4.2 的 `test_user_interaction.py` 真按键模拟正是亡羊补牢（一跑就抓到 SIGSEGV）。
4. **禁止在腐坏结构上堆补丁。**
   - 修复时若发现**结构性根因**（如 `clear()` 重建 popup 导致 Backspace 吞字符、`self._search_worker` 覆盖引用致 QThread 被 GC），**优先重做该结构**（引用保活池 / popup 增量更新），而非在崩处加 try/except 兜底。
   - 判据：如果一处修了之后还需要"再补一个补丁才能稳"，就是腐坏结构——提重构任务，进架构契约文档。

### 规矩 3：写域分离（同一文件 = 串行）

- **同一文件的改动串行化**（依赖链显式声明），**不同文件才并行**。
- 并行的前提是文件级无重叠 + 打包阶段 `compileall` + 共改文件交叉点核对（changelog_1.4.0 §十二式）。
- 1.4.2 最高危串行点：`workshop_tab.py`（t1 → t2 串行：QThread 守卫先落地，游戏搜索域在其上重做 popup 行为）。
- 共享文件热点表见 §六。

### 规矩 4：2.0 准备（重构时机未定，但天天在准备）

- 用户已宣告将重构（2.0，时机未定）。一切新增功能 / 修复必须：
  1. 在代码注释中标注 **「临时性 / 迁移友好」**：临时性补丁注明"2.0 随 <结构> 重做时移除"；迁移友好的部分注明契约边界（2.0 可直接搬走的设计）。
  2. **核心逻辑文档化**：交给架构契约文档任务（t3，stab-fixer）——核心模块的边界 / 不变式 / 依赖 / 拆分目标沉淀成文档，2.0 重构时这是唯一的迁移地基。
- 换语言级重构（架构重构）列为 **2.0 终极议题**，待讨论组裁决（不做预热实现）。

### 规矩 5：核心成员稳定制（专人专项）

**域 owner 一旦确定，跨迭代尽量保持同一成员持续负责同一域，不轻易更换。**

- **理由**：有该项目 / 该域经验的 agent 更能发现潜在不足与下一步改进方向——记得每个设计决策的"为什么"、踩过的坑、历史 bug 模式，**域知识复利**；换新成员等于把这些经验清零重学。
- **换帅只允许三种情形**：① 成员长期不可用；② 域被重构吞并（域本身消失）；③ 所有者连续两轮交付质量不达标。
- **交接不可避免时**：必须先移交**「域契约文档」**（不变式 / 状态机 / 已付学费清单——即该域历史上踩过并修复的 bug 模式与设计决策理由），**禁止默默换人**。域契约文档与架构契约文档（t3）同源：核心模块的边界文档同时是域 owner 的交接物。
- **与规矩 1 合读**：**规矩 1 管"一件事归谁"**（bug 出现时交给域成员修）；**规矩 5 管"一个域长期归谁"**（跨迭代不换帅）。两条共同构成 stream-aligned 域 owner 的端到端责任制。
- **反例警示**：swdm-138 → swdm-142 换血时，成员名整体重映射（packager=installer-fixer / scribe=recorder / fixer=search-fixer / gui-checker=gui-tester / core-checker=core-tester）——这是团队级换血而非单域换帅；若要做的是单域换帅，必须走域契约文档移交流程，不能只改一个 assignee 名字。

## 二、团队拓扑（Team Topologies 映射）—— 规矩 1 的论据

Team Topologies 定义四类团队与三种交互模式；SWDM 的多智能体团队按下表映射（两届团队对照）：

| Team Topologies 类型 | 定义 | SWDM 映射（swdm-142 / 1.4.2） | 历史对照（swdm-138） | 为什么这样放 |
|---|---|---|---|---|
| **Stream-aligned**（价值流团队） | 面向一条用户价值流，端到端 build+run+fix，不做交接 | **ux-fixer**（游戏搜索域 t2，规矩 1 的践行）· **stab-fixer**（稳定性 t1 + 架构契约 t3）· **qa-indept**（复测 t6，第一线用户视角） | search-fixer · gui-tester · core-tester · installer-fixer | 面向"用户交互层 bug"价值流，按**域**切分（不是按"修 bug"切分），域 owner 端到端守自己的域——这正是规矩 1 的组织载体 |
| **Platform**（平台团队） | 提供自服务内部平台，被消费不来回开会 | **ui-designer**（t4 设计令牌 / QSS 2.0 + t7 PCL2 视觉对比与 2.0 技术栈） | （1.4.0 打包基建由 installer-fixer 兼任） | 设计令牌与 QSS 是被所有修复任务**消费**的自服务平台，不是某个 bug 的私有修复 |
| **Enabling**（赋能团队） | 教 stream-aligned 团队钓鱼 | **process-doc**（t5 继任者文档 / 流程体系） | recorder（工程记录 + 信息中枢） | 文档与流程产出被所有成员引用，自己不修 bug（赋能而非代劳） |
| **Complicated-subsystem**（复杂子系统团队） | 深度专业子系统 | （1.4.2 无独立设置；历史上由 **core-tester** 守下载引擎 / provider 链 / 状态机） | core-tester（provider 抽象层 t21/t28） | 下载引擎 / 并发 / 熔断是深度子系统；**用户交互层迭代不设此团队，但预留接口：凡触碰 `swdm/core/downloader.py` / `providers/` 的任务须标"核心域"并走串行队列** |

**三种交互模式**（团队类型之间的合法协作方式）：

1. **Collaboration（协作）**：同文件 / 同行为联动的任务之间，成员直接对话（`agent_teams_send_message`），**不经 captain**。范例：1.3.9 t12（游戏输入/标签过滤）× t13（切换游戏标签刷新）共用 `workshop_tab.py`，任务描述互相点名联动点（tag_bar 选中状态与 tag_edit 文本一致性）；1.4.2 t1 × t2 同文件串行 + 契约对接。
2. **X-as-a-service（即服务）**：ui-designer 的设计令牌是自服务产物：修复任务按令牌取色 / 间距；改动令牌本身是独立任务（t4）。出包链（PyInstaller → ISCC → 冒烟）是 captain 的"即服务"能力，成员产出代码后由 captain 集成。
3. **Facilitating（促进）**：process-doc 写继任者文档与流程规矩、qa-indept 跑独立复测——**赋能而非代劳**：qa-indept 不写产品代码（只验证），process-doc 不改他人域的代码。

**反模式（禁止）**：
- ❌ stream-aligned 成员去改平台资产（修复任务顺手重定义令牌 / 重构 QSS）——提 ui-designer 评审。
- ❌ enabling 成员代写修复代码（process-doc 去修 workshop_tab）。
- ❌ 复测员既写代码又复测自己写的（见 §四 SDET/QA 分离）。
- ❌ **设泛 bug 修复专员**（规矩 1 的直接违反）。

## 三、多智能体实验教训（SPOQ + 执行接地）—— 规矩 2.3 的论据

> 来源：SPOQ: Specialist Orchestrated Queuing for Multi-Agent Software Engineering（arXiv:2606.03115）；execution-grounded verification（AgentForge：每条代码改动必须先在沙盒中真实执行存活，才能向下游传播）。以下既是对外方法论的共识，也是 SWDM 历史迭代**已经独立验证过**的实践。

### 3.1 DAG 波次调度（Wave-Based Topological Dispatch）

- 任务依赖建模为**有向无环图（DAG）**，拓扑排序算执行波次：**同波次并行，跨波次串行**（与规矩 3 一致：同文件 tasks 落同一波次的串行链）。
- 创建任务时**显式声明 `dependencies: [tX, ...]`**，调度器自动放行；无依赖的 Wave 0 并行跑。
- 历史波次范例（1.4.1）：

  ```
  Wave 0（并行）：t32 GGNetwork 补测 · t33 详情缓存 · t34 预取 · t35 剪贴板 · t37 库更新检查 · t38 账号 provider · t39 README · t40 技术债 · t41 失败原因 · t42 手册
  Wave 1：t43 打包（依赖全部功能任务）
  Wave 2：t44 GUI 复测 · t45 核心复测（依赖 t43 打包终态）
  Wave 3：t46 六方交付评审（依赖 t44 + t45 双轮复测）
  ```
- 关键路径 = 加权最长路径；排期先算关键路径（1.4.2 关键路径：t1 → t2 → qa 复测 → 打包 → 双轮复测 → 评审；t3/t4/t5/t7 并行支线）。

### 3.2 双验证闸门（Dual Validation Gates）

- **执行前（规划验证）**：任务分解是否原子、依赖是否无环、成功标准是否可测、风险是否识别、集成策略是否清晰。**规划错误向下游传播且修复昂贵**——SWDM 要求任务描述含 inFile 行号锚点 + 约束 + 验证命令 + 依赖（预研粒度范例：`docs/research/plan_1.4.2_impl.md`：文件:行号 + 工时 + 风险）。规矩 2.2「契约先行」是这条的加强版：契约即规划闸门的可检对象。
- **执行后（代码验证）**：编译通过 / 测试存在 / 测试通过 / 需求保真 / 错误处理。SWDM 把它加强为**执行接地**（§3.3）。
- 讨论组（功能评审）= 规划闸门的人员版：三原则（精简 · 以用户体感为中心 · 保证基本功能正常运行）逐条裁决，零原则性反对才放行（t23 / t31 范式）。

### 3.3 执行接地（Execution-Grounded Verification）—— SWDM 第一硬纪律

1. **改完即跑**：每个功能任务自带测试，同批产出（脚本式 `check()` + `RESULT:` 行，dev_test §3.1）。
2. **真实路径优先**：覆盖线程 / 回调等"看起来对"的路径用真线程复测——1.4.1 A6 教训：`QMetaObject.invokeMethod(Q_ARG(list,...))` 在本机 PySide6 无 QMetaType，完成回调**从未触发**，单测直调收尾根本看不见这个盲区，t44 沿真实线程路径复测 8 项才抓到。
3. **真按键才算交互测试**（规矩 2.3）：API 层断言不发现用户上手才有的 bug（1.4.1 86+111 项全 PASS → 用户 4 个交互 bug 的教训）。
4. **失败必须定位定性**：run_all 任何 FAIL 经逐项定位确认"环境性 / 测试固件 / 代码回归"三选一，环境性单独重跑确认（1.4.1 `test_stress` 1_SLOW 与 `test_game_dir_e2e` 看门狗均如此定性）。
5. **不通过不传播**：复测未两轮通过，不打包、不评审、不交付。

### 3.4 Human-as-an-Agent（HaaA）

- 用户是**编排在调度回路里的高价值智能体**：需求输入（报告 bug）→ 规划参与（讨论组三原则代表用户体感）→ 执行中可咨询 → 交付前确认（人工目检 9 张截图、真机验收）。
- 交付时**明确列出需要用户人工确认的项**（user_interaction_scenarios §十七），不把"自动化做不到"静默吞掉。

### 3.5 任务粒度

- 单任务 1-4 小时（SPOQ 实践值）。✅ 1.3.8 t1-t4（每个 <15 行 + 自测）；❌ 1.4.1 t43 打包任务连续 4 次超时（重型构建 + 长回归压成员单轮，见 §七）。

### 3.6 AgentTeams 运维教训（本机实测）

- **会话模型路由切换后，已有成员的路由不会自动更新**：报 "no adapter registered for provider" 且重试无效；切换 provider / model 后必须重建成员或显式更新路由。
- **成员间直接通信**：`agent_teams_send_message(to=<teammate>)` 直达邮箱并唤醒，**不经 captain**（协作模式靠这条）。
- **消息纪律**：完成或受阻向 captain 发**一条**报告（含 `source_task_id` + `source_attempt_id`）；不发纯确认；新工作单元用任务创建 / 重派，不用消息催。
- **stale attempt**：`agent_teams_update_task` 报 stale = 任务被重派或 captain 接管，**立刻停手**，不拿旧 attempt 贴新结果。**claimed 不能跳 completed**：先 in_progress 再终态。
- **中继协调范例**（无 captain 在环）：1.3.8 recorder 中继 t9 讨论结论并入 t5（打包中时序冲突）——转达 → 并入 → 回信确认 → 旧记录标"已过期"；**信息以最新回信为准，过期记录显式标注**。

## 四、SDET / QA 分工教训 —— 规矩 1 的验证侧对应

### 4.1 开发者自测 ≠ 独立复测（必须分离）

| 角色 | 职责 | 禁止 |
|---|---|---|
| 域 owner（开发者 / SDET 侧） | 写代码 + **写测试**（含真按键交互测试，规矩 2.3）+ 自测通过 | ❌ 自测通过就宣称交付 |
| **qa-indept（独立复测员）** | **不写任何产品代码**，只验证；两轮视角互补复测 + exe 冒烟 | ❌ 改被测代码（发现问题建任务给域 owner——规矩 1） |
| 讨论组（评审方） | 三原则逐条裁决 + 投票 | ❌ 只看自测数字（1.4.1 教训） |

### 4.2 两轮连续复测（交付闸门的测试侧）

用户规定："bug 测试员连续两轮复测均无任何异常"——SWDM 的两轮是**视角互补**而非重复：

| 轮次 | 视角 | 历史范例（1.4.1） | 关键纪律 |
|---|---|---|---|
| 第一轮 | **GUI / 用户视角** | t44：56 + 30 项 + exe 冒烟（pid 11184，8s/10s 双检查点存活） | 从用户操作序列验证（user_interaction_scenarios 剧本），不只看单测；**必须含真按键交互层**（规矩 2.3 的复测版） |
| 第二轮 | **核心逻辑独立视角** | t45：111 项独立检查 + skip 基线 69/69 | **刻意不复用各功能任务的自测 mock**——用独立夹具重验，否则自测盲区（如 A6）原样继承 |

- 两轮都跑 `run_all.ps1` 全量回归 + 与上版基线逐项核对（口径：零新增失败 + 既有非回归逐项定性）。
- 产出 `docs/retest_round1_gui_<版本>.md` + `docs/retest_round2_core_<版本>.md`，作为六方评审输入。

### 4.3 覆盖面教训（历史盲区清单）

1. **真实线程路径**：单测直调收尾看不见回调从未触发的死接线（A6）→ 复测走点击 → worker → 回调完整路径。
2. **弹窗时序**：模拟 QMessageBox 非真实阻塞，弹窗时状态必须在桩内捕获（dev_test §四.9）。
3. **offscreen 天盲区**：真实剪贴板 / 托盘态 / 主题跟随系统 / 视觉布局——**不能因为测不了就说没问题**，进人工补测清单交给用户（user_interaction_scenarios §十七）。
4. **全量回归不只测改动点**：必须含功能间关联交互（`test_cross_features.py` 26 项：搜索+标签叠加、翻页+排序、下载中切 Tab、closeEvent 三分判定）——用户规则 1 的直接产物。
5. **夹具漂移**：真实 mod 更新 / Steam 页面结构变迁让硬编码夹具假失败（`test_legacy_format` / `test_page_parser`）→ 夹具随证据（Wayback 快照）重写，不删断言。

## 五、成员专精原则

- **一人一域**：成员只接自己域的任务（及明确声明的 in-scope 文件）。域 = 规矩 1 的 owner 名册。
- **域所有者即文件所有者**：触碰他人域的文件前建任务并让域 owner 知悉（协作模式，§二）；同文件并行 = 禁止（规矩 3）。
- **跨迭代稳定**（规矩 5）：域 owner 不轻易换帅（仅三种情形）；换帅必须先移交域契约文档。
- **专精不垄断**：完成自己域后可接相邻域的明确任务（如 recorder 兼中继协调），但不得跨越写域分离线去改他人正在改的文件。
- **换血对照**（swdm-138 → swdm-142）：packager=installer-fixer · scribe=recorder · fixer=search-fixer · gui-checker=gui-tester · core-checker=core-tester。历史文档出现的是旧名，读时自行映射（团队级换血 ≠ 单域换帅，后者须走域契约文档移交）。

## 八、captain 的职责边界

### 8.1 captain 做什么

1. **集成**：拆任务（含依赖图与 in-scope）、冲突检查（`compileall` + 交叉点核对）、把成员产出合并为可交付整体。
2. **构建与交付**：PyInstaller → ISCC → `%TEMP%` 冒烟（dev_test §四.4 沙箱陷阱）→ 版本号双端核对 → git commit / tag vX.Y.Z / 推送（token 只在 captain 处，频道见 dev_test §二）。
3. **闸门主持**：四要素核对（全量回归 / 讨论组 / 版本号 + changelog / 两轮复测）；六方评审收票（1.4.1 t46 范式：主持 + captain + 打包 + GUI 复测 + 核心复测 + 文档，6/6 零反对）。
4. **重型任务兜底**（见 §8.3）。
5. **对用户唯一出口**：交付物、人工目检提醒、已知限制披露。

### 8.2 captain **不做**什么（不包办）

- ❌ 不写成员域的代码（除非成员连续失败且重派后仍失败，此时以"接管"方式显式 `reassign_task(assignee="captain")` 并声明）。
- ❌ 不做成员的自测（开发者的测试由开发者写，含真按键交互测试）。
- ❌ 不做复测（两轮复测是 qa-indept 的活；captain 只收结论与跑构建冒烟）。
- ❌ 不在成员工作途中改其 in-scope 文件（破坏写域分离，规矩 3）。
- ❌ 不替讨论组裁决功能取舍（主持方 + 评委投票；captain 的裁决权仅在"议程外提问当场定案并写进 plan"与"交付闸门收口"）。
- ❌ 不当泛 bug 修复专员（规矩 1 适用于所有人，包括 captain）。

### 8.3 每个重型任务必须有 timeout 应对（硬性规矩）

**教训（1.4.1 t43）**：打包任务（PyInstaller + ISCC + 手册核验 + 全量回归 + 冒烟）压在 packager 单轮，**连续 4 次轮次超时**，最终 captain 接管打包才闭环。结论：

1. **拆**：重型任务按阶段拆成多个任务（构建 → 回归 → 冒烟 → 手册核验），每阶段单任务可单轮完成（≤ 1-4h 粒度，§3.5）。
2. **timeout 应对预案写在任务描述里**：超时后的降级动作（如"ISCC 超时则单独重跑构建步骤并报告；回归超时则分流到 skip 基线单跑"）。
3. **连续 2 次超时 = 升级信号**：captain 接管或重派（而非第三次原地重试）。
4. **长回归不得与构建同任务**：run_all 全量（10-30 分钟）独立成复测任务。
