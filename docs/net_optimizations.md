# 网络请求模式盘点与优化建议（SWDM 1.3.6 基线）

> 盘点对象：`swdm/core/steam_api.py`、`steamcmd_engine.py`、`downloader.py`、
> `gui/workers.py`、`gui/detail_dialog.py`。结合 `research/steam_429_403_research.md`
> （34 次本机实测）与已沉淀结论。

## 当前模式盘点

| 环节 | 实现 | 现状 |
|---|---|---|
| 全局节流 | `_Throttle`（steam_api.py:81-108），最小间隔 2.0s，`bump` 上限 60s，`decay` 每次 -2s | 串行化所有社区页请求 |
| 端点差异化节流 | `_endpoint_throttle`（:274），`/sharedfiles/` 6s、`/workshop/browse/` 2s | 已按端点分级 |
| 429 处理 | `_community_get`（:313-331）：退避 30s 起、渐进 90s 封顶，最多 2 次重试 | 实测 429 从不带 Retry-After（10/10），冷却窗 >24s |
| 403 处理 | 快速失败不重试（:303-312），上层用过期缓存兜底 | IP/边缘层封禁重试无用 |
| 请求头 | 必带 `Accept-Language`（:218-222），已修复指纹层 429 | 关键修复已落地 |
| 详情页缓存 | `DetailPageWorker._page_cache`（detail_dialog.py:356），TTL 300s | 进程级，缓解重复请求 |
| 列表缓存 | `get_api_cache()`（api_cache.py），browse 命中深拷贝后返回 | 已避免缓存污染 |
| enrich | 每 50 ID 一批 `get_file_details`（:345+），复用 session | 批量化已做 |
| 图片加载 | `ImageLoader`（workers.py:108+）QThreadPool 并发，缓存 300 张 | 主线程有同步下载回退（缺陷，见 algo 文档 #3） |

## 优化建议

### N1. 请求取消：用户切游戏/翻页时在途请求作废（高优先）
- **现状**：`BrowseWorker`（workers.py:26+）一旦 start 即跑到完，用户快速切
  游戏时旧请求仍占着节流配额排队跑完，新结果可能盖在旧结果之后到达
  （`_pending_refresh` 只解决了"请求被丢弃"，没解决"乱序到达"）。
- **改法**：worker 持 `QAtomicInt` 代际号，`items_ready` 发射前比对当前代际，
  过期直接丢弃；或用 `requests` 的 `Session` + 中断信号。
- **收益**：快速操作时不再出现"结果跳来跳去"；省下被废弃请求的节流等待。

### N2. 429 冷却期全局熔断，避免连锁退避（高优先）
- **现状**：`_throttle.bump` 把最小间隔顶到 30-60s，但所有线程仍会调
  `acquire()` 阻塞等待；详情页预取、依赖下载、图片回退都在同一节流器上排队。
- **改法**：熔断期间（记录 429 时刻）新请求直接快速失败走缓存兜底，而不是
  全部 sleep 排队；熔断窗口（实测 >24s，取 30s）过后自动放行。
- **收益**：限流期间界面不假死，缓存数据仍可用。

### N3. 图片请求不进社区节流器（中优先）
- **现状**：图片回退走 `api._session.get`（workers.py:156-158）虽不经
  `_throttle.acquire()`，但与社区页共用同一 session 连接池；且主线程同步。
- **改法**：图片用独立 session（无 cookie、独立连接池）+ 全程子线程，
  与社区页请求完全隔离。
- **收益**：图片下载不与列表抓取争抢连接；主线程不阻塞。

### N4. 详情页预取与点击合并去重（中优先）
- **现状**：悬停 400ms 预取（workshop_tab.py:303-305）与点击详情都发请求；
  快速划过列表时预取了多个不点的物品，浪费配额。
- **改法**：预取前检查 `_page_cache` 已有则跳过（已做，:888）；
  追加：同一物品 5s 内重复请求合并为一次（in-flight 去重）。
- **收益**：快速划过列表时的无效预取消失。

### N5. 节流参数可配置 + 自适应（低优先）
- **现状**：2.0s 全局最小间隔为硬编码。
- **改法**：从配置读，且连续成功 N 次后自动收紧（当前 `decay` 每次只 -2s，
  从 60s 回落到 2s 要 30 次成功请求，太慢）。
- **收益**：恢复到全速更快。

## 不建议改动
- **403 快速失败 + 缓存兜底**：实测重试无用，当前策略正确。
- **`Accept-Language` 必带头**：核心 429 修复，勿删。
- **steamcmd 串行化 `_engine_lock`**：多任务竞态的根治方案（1.3.4）。
