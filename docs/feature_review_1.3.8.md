## A. t1 搜索低命中率提示文字

**现状**：标题命中率 <0.3 时展示「Steam 搜索仅匹配标题；作者搜索请使用详情页或 API key 模式」。

- search-fixer：**保留**。这条提示正是本次用户 bug 的"解药"——用户搜作者名得到一堆无关结果时，没有解释会以为程序坏了。措辞可柔化、缩短为「Steam 搜索仅匹配标题；按作者搜索请用详情页或 API key 模式」。
- core-tester：**保留但缩短**。"API key 模式"对匿名默认用户无意义，建议精简为「Steam 搜索只匹配标题；按作者找请打开物品详情页。」
- gui-tester：**改进措辞**。时机对，但"API key 模式"是黑话。建议改成「Steam 搜索只认标题，已按作者名帮你过滤；想精确搜作者，可在设置页填写 Steam API Key。」——把动作指向具体入口。另指出两处提示（低命中 / 0 命中回退）措辞不统一，建议合并成一套。

**结论：改进（保留提示，统一并缩短措辞）**
- 三方一致认为提示必须保留（消除"搜索坏了"的误解），但对措辞有分歧：两方认为应去掉"API key 模式"黑话，一方认为应保留并指向设置页入口。
- 理由：提示出现的时机正是结果看起来无关时，属于净增益；但当前措辞对匿名用户不友好。
- 建议：合并两处提示为一套，统一为「Steam 搜索只匹配标题，已按作者名过滤；想精确搜作者请打开物品详情页。」（API key 引导作为可选项，由 t8 定）。

## B. 0 命中作者回退的空态提示

**现状**：`apply_browse_search_fallback`（steam_api.py:828-835）在 0 命中且回退过滤后仍为空时返回 (items, SEARCH_LOW_HIT_HINT)，列表非空但展示无关结果；空列表文案是"没有匹配的物品…或触发限流"，两种情况都会让用户误以为"搜索坏了/被限流"。

- search-fixer：**该补空态**。如果用户搜的作者确实没有 mod，应明确提示「未找到该作者的 mod」。<10 行小改，体验闭环，建议纳入 1.3.8（可接）。
- core-tester：**改进（补空态提示）**。补一行"未找到标题或作者含「X」的 mod"，几行小改动消除误解。
- gui-tester：**添加，纳入 1.3.8**。回退为空时返回空列表 + 明确空态文案；正好是 t3 G1 空态分支的延伸，联动改最干净。

**结论：改进（补空态）——建议纳入 1.3.8**
- 三方一致，无分歧。这是 t1 修复的体验闭环，改动小、风险低。
- 落地人：search-fixer（在 t5 打包前并入）。

## C. F7 hide_keywords 标题关键词过滤

- search-fixer：**保留**。对重度用户（批量浏览、屏蔽废弃 mod）有实际价值；但入口在设置页较深、工坊页无即时反馈，建议 1.3.9 在卡片右键菜单加"屏蔽此类标题"快捷入口。
- core-tester：**保留**。降噪实用，默认空串不侵入；低频配置项，当前入口够用，不需要更显眼。
- gui-tester：**保留**。用户报告的 bug 之一就是噪音多，这功能直接降噪；入口在设置页"高级"区够用，不建议提到工坊页（增加主界面复杂度）。小改进：状态栏标注"已隐藏 N 个标题含屏蔽词的 mod"，让沉默过滤可见（当前过滤完全无感知，用户不知道为什么结果变少了）。

**结论：保留**
- 三方一致保留，无删减意见。
- 可选小改（本版即可，非必须）：工坊页状态栏加"已隐藏 N 个"计数，让沉默过滤可见。
- 1.3.9 再考虑卡片右键"屏蔽此类标题"快捷入口。

## D. 调试 Tab 是否默认隐藏

- search-fixer：**1.3.9 做**。建议 config 开关 `debug_tab_visible` 默认 false + 设置页"显示调试页"复选框；涉及主窗口构建逻辑，1.3.8 不动（回归风险）。
- core-tester：**改进：默认折叠**。调试 Tab 对排查（429/下载失败）很有用，项目重度依赖日志自证，不能删；默认展开增加普通用户噪音，折叠/隐藏默认即可。
- gui-tester：**默认隐藏 + 设置页开关**。config 里已有 `logging.show_debug_panel` 字段但没被用；普通用户 5 个 Tab 已偏多，调试页是纯噪音；但排障时导出日志有用，不能删。注意测试里有多处直接访问 `win.debug_tab`，隐藏需同步改测试（test_all_buttons 遍历 findChildren，隐藏后按钮不可见会跳过——这反而是对的）。

**结论：改进（默认隐藏 + 设置页开关）——建议留 1.3.9**
- 三方方向一致：不删、默认隐藏、保留排障能力。
- 时序有分歧：search-fixer 明确主张 1.3.9（回归风险），gui-tester/core-tester 建议这版。
- 倾向留 1.3.9：涉及主窗口构建逻辑与多处测试同步（`win.debug_tab` 引用），1.3.8 应把精力集中在 B/F 等高优项。由 t8 结合剩余时间定。

## E. 下载页 5 个批量按钮是否过多

- search-fixer：**保留**。对应真实下载管理场景（1.3.7 F1 批量队列），每个都有独立语义，合并进"更多"菜单反而增加点击成本；当前布局已被 test_all_buttons 覆盖验证。
- core-tester：**改进：收纳**。五个操作对应五个不同状态，状态机测试已全覆盖，删任何一个都丢能力。建议保留"暂停/继续 + 取消全部"为主按钮，"重试失败 / 清除已完成"收进"批量操作"菜单，降低视觉噪音。
- gui-tester：**改进：合并暂停/继续为单状态按钮**。pause_all/resume_all 互斥启用（G3 的 `_sync_batch_buttons` 已驱动），两按钮永远只有一个能用，合并成"⏸ 暂停全部 / ▶ 继续全部"单按钮更精简；其余三个保留。

**结论：改进（合并/收纳）——建议留 1.3.9**
- 三方一致功能不能删（都有独立语义、已被测试覆盖），但对"如何精简"有三种方案：不动 / 菜单收纳 / 合并互斥按钮。
- 倾向留 1.3.9：1.3.8 先不动（布局已被 test_all_buttons 覆盖，改动会牵动 G3 状态同步与测试）；1.3.9 优先采用 gui-tester 的"暂停/继续合并单按钮"（最精简），可叠加 core-tester 的菜单收纳。

## F. t4 三个待修中大 bug 是否纳入 1.3.8

- search-fixer：**全部留 1.3.9**。cancel 微秒窗口需高频取消才可能命中（偶发）；SQLite 锁超时只在多实例并发写时出现（应用单实例）；on_throttle_signal 覆盖只在两个 manager 共享 engine 时出现（应用只有一个）。三者都不触碰"基本功能正常运行"底线，1.3.8 的核心价值是兑现用户报告的两个 bug + 自测小修，先发布。
- core-tester：**SQLite 锁超时纳入 1.3.8，另两个留 1.3.9**。B（mod_library.py:154-157）是单行改动（连接 timeout 抬到 30s），磁盘繁忙/多库场景下能防止队列假死，性价比高；A（downloader.py:392-393 popleft 与 _active 赋值间竞态）触发概率极低且无数据风险；C（downloader.py:114）只在两 manager 共享 engine 时触发。
- gui-tester：**纳入 1.3.8**。SQLite 锁超时：下载线程写库 + 用户同时浏览/导入库是常见交互，触发就是"database is locked"可见失败；on_throttle_signal 覆盖：一行修（改 append 或显式赋值语义），是正确性 bug；cancel 微秒窗口：真实复现概率低但取消是高频操作，若不修至少加防御（取消后不再登记 _done），时间紧可留 1.3.9，但前两条建议这版收。

**结论：SQLite 锁超时纳入 1.3.8；on_throttle_signal 倾向纳入；cancel 留 1.3.9**
- SQLite 锁超时：2/3 支持纳入（search-fixer 反对，理由是"应用单实例"——但下载线程写库 + 主线程读库同一进程内也会锁竞争，core-tester/gui-tester 的判断更贴合实际），且改动极小。**建议本版收**。
- on_throttle_signal 覆盖：gui-tester 必收（一行修的正确性债），core-tester 排最后未反对。**倾向本版收，由 t8 定**。
- cancel 微秒窗口：2/3 主张留 1.3.9。**留 1.3.9**，1.3.8 可考虑加"取消后不再登记 _done"的防御（可选）。
- 最终由 t8 结合复测结果与剩余时间决定。

## G. test_page_parser 旧夹具处理

- search-fixer：**重写为基于真实 Wayback 快照的夹具**（与 research 三快照实证结论对齐），否则它永远 FAIL、稀释回归信号；重写前可先标记 skip。
- core-tester：**删除过时断言，保留仍有效的**。基于"浏览页有 requiredtags 链接/tagFilter 容器"的断言测的是已被 Wayback 证据推翻的从未存在的结构，留着只会误导——不是"回归保护"而是"错误假设固化"；仍覆盖真实解析路径的部分重写到当前结构。
- gui-tester：**重写（不要删）**。parse_available_tags 是工坊标签栏的生产路径，必须有回归保护；真实页面回归（描述/评论部分）一直 PASS，说明解析本身没退化。从 tests/fixtures 里的真实浏览页快照抽一段真实侧栏片段替换合成 HTML 即可；删掉等于这段路径零覆盖，下次改标签解析会静默回归。

**结论：改进（用真实快照重写，删除纯验证旧结构的断言）**
- search-fixer 与 gui-tester 一致主张重写（保留覆盖），core-tester 主张删过时断言。
- 折中：用 tests/fixtures 的真实快照侧栏片段替换合成夹具，同时删除纯验证已推翻结构的断言——既消除持续 FAIL 的噪音，又保住 parse_available_tags 的回归保护。
- 时序：1.3.8 若有余力可做，否则 1.3.9；重写前先 skip 避免稀释信号。

## H. 该加但没加的功能

- search-fixer：
  1. 作者搜索的彻底兑现——0 命中回退是补丁，正解是"查看该作者全部 mod"（作者作品列表页），建议 1.3.9 在详情页加入口。
  2. 卸载侧 t2 已用 AppMutex 解决进程残留；可补"卸载完成后打开反馈/告别页"提升体感，优先级低。
- core-tester：**一个该确认的缺口——卸载残留的数据目录**。t2 修的是"进程占用导致卸载被忽略"，但"卸载残留"也可能指 %APPDATA%\SWDM 下的库 DB、图片缓存、日志、steamcmd 工作区。请确认 installer/swdm.iss 是否清理了这些目录；若没有建议加卸载时删除（或至少提供选项）。
- gui-tester：
  1. **设置页"打开数据目录"按钮**——用户报告的"卸载残留"本质是数据目录散落用户看不见；t2 修了互斥量让卸载能关程序，但用户仍需一键定位残留文件。小改、与卸载主题直接呼应，建议纳入 1.3.8。
  2. **库页"导出列表"应导出当前筛选结果**——_export_list 导出全部记录而非当前过滤视图，与按钮位置（过滤工具栏旁）的预期不符，小改，建议纳入 1.3.8。
  3. 工坊页"下一页"在最后一页仍可点——已让空列表+page>1 显示"已到最后一页"提示（G1），按钮未禁用；匿名 browse 拿不到总数，保持现状+提示可接受。

**结论**
- **卸载数据目录清理：经 installer-fixer 核实已实现**（t2 时通读 installer/swdm.iss 全文）：`CurUninstallStepChanged` 在 `usPostUninstall` 阶段（1）始终删除程序部署的 steamcmd 子目录；（2）按"保留用户数据"复选框（卸载前弹窗同步、进度页可改主意）决定是否删除整个 `%APPDATA%\SWDM`，且带三重安全校验（必须以 `\SWDM` 结尾、必须含 config.json / library.db / logs\swdm.log 之一特征文件、安装目录含源码时整体跳过）。因此 core-tester 的关切已被覆盖，无需新增；体感上可通过 gui-tester 的"打开数据目录"按钮补强可见性。
- **建议纳入 1.3.8 的小改**：①设置页"打开数据目录"按钮；②库页导出当前筛选结果。（均为小改，与用户报告的卸载/噪音主题直接呼应。）
- **留 1.3.9**：①作者作品列表页（详情页入口，作者搜索的正解）；②卸载完成告别/反馈页。
