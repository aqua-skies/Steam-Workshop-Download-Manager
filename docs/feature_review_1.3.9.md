## A. 1.3.8 遗留 P1 / P3 是否纳入 1.3.9

**A-P3（on_throttle_signal 被覆盖，downloader.py:114）**
- search-fixer：本版收。一行正确性债，append 语义改动小，有 test_core_sweep 托底，风险近零。
- core-tester：本版收。改法：`__init__` 的 `self.engine.on_throttle_signal = self._on_throttle_signal` 改为追加订阅（引擎侧单回调改 list 遍历，约 3 行）。风险低——限流信号处才调用，改 list 后空列表/单订阅与单回调等价，engine_concurrency 与 throttle 测试覆盖。**与 P1 不同，P3 有真实触发路径**（多 manager 共享 engine，如依赖下载与主队列分离时）。
- gui-tester：本版收，一行正确性债零风险。
- recorder：本版收。1.3.8 讨论组已倾向收，t17 任务描述也点名"至少 P3"，继续拖无收益。

**结论：改进——本版收 P3。** 5/5 一致，无分歧。

**A-P1（cancel 微秒窗口，downloader.py:392-393）**
- search-fixer：留 1.3.10。>15 行、触发概率极低且无法稳定复现，本版赶打包不宜动并发状态机；同意 recorder 的"取消后不登记 _done"廉价防御可让 t14 顺手加。
- core-tester：留后版。窗口仅在 popleft 与 _active 赋值之间，无用户可感知后果；正确修复需引入 pending-cancel 集合 + 派发前检查（>15 行，涉及状态机核心路径），收尾阶段不宜动。
- gui-tester：留 1.3.10；建议 t14 顺手加"取消后不登记 _done"廉价防御本版收下（若已收更好）。
- recorder：留 1.3.10。>15 行改动，1.3.8 讨论组 2/3 主张留后版；1.3.9 已有 12 个用户 bug 要修，排期不应再扩。建议 t14 修速度采样时顺手加防御。

**结论：删减（从本版移除）——P1 留 1.3.10；本版改收"取消后不再登记 _done"廉价防御（t14 顺手带）。** 5/5 一致。

## C. 新 bug 引出的功能取舍

**C-① mod 库按游戏分类（u14）是否与"精简"冲突**
- core-tester：**不冲突，建议小改收。** 关键洞察：appid 过滤下拉早已存在（library_tab.py:72-75 + refresh 填充），真正缺口是**展示层用裸 appid 数字**（"4000" 而非 "Garry's Mod"：过滤下拉行 165 与库行文本 223）。用 games.game_name() 渲染即可，无需新增列/分组结构，符合精简原则。（t14 已定位到行级。）
- gui-tester：t14 已在展示层落地（game_name() 下拉），u10 联动测试验证 records_removed 与其无冲突。同意保守实现，不加新大功能。
- search-fixer：支持保守实现（游戏列 + 筛选下拉，不做分组折叠）。用户明确报告这是基本可用性问题——"精简"针对功能堆砌而非必要的信息组织。
- recorder：不冲突，建议做。用户明确报告"不同游戏的 mod 没有分类"是基本功能可用性问题（找不着自己的 mod），优先级高于精简原则。建议实现保守：游戏列 + 筛选下拉即可，不做复杂分组树。

**结论：添加——本版收，保守实现（game_name() 渲染 + 筛选下拉，不加分组树）。** 5/5 支持。core-tester 的行级定位把"新功能"降维成"展示层修正"，与精简原则不冲突。

**C-② 下载页 5 个批量按钮本版是否动**
- 四方一致：**本版不动**。五个按钮各对应一个状态机操作（pause_all/resume_all/retry_all_failed/clear_completed/cancel_all），合并暂停/继续为单切换钮需引入状态判断 + 图标切换，收益有限；且 _clear_done/_remove_row 刚改、_sync_batch_buttons 与其耦合，排期满。留 1.3.10 polish 批。

**结论：保留（本版不动）。** 5/5 一致。

## D. GameSearchClient 1.2s 间隔 vs 联想手感

- search-fixer：**降底线间隔 + 指数退避组合**。t12 修复后本地匹配已零延迟即时出候选、下拉弹出时机已统一，网络部分不再是体感瓶颈；剩余延迟感来自 1.2s 最低间隔。建议降到 0.6-0.8s 并复用 1.3.7 O5 的 _Throttle 熔断器做失败退避（storesearch 被熔断时本地匹配兜底，体感不中断）。**不建议直接降到 350ms**——storesearch 是匿名接口，没有速率保障。
- gui-tester：降到 0.6-0.8s + 熔断退避（而非纯二选一）。t12 的联想已做本地即时匹配 + 模糊评分，网络层慢一点用户基本无感；但纯加长固定间隔会在网络抖动时连续卡顿，熔断退避更稳。
- core-tester：**建议不降间隔，改加本地即时层。** storesearch 熔断的代价是整页搜索失效，1.2s 是防熔断的护城河，降到 0.3s 有熔断风险（本机出口 IP 已被 Steam 限过）。正确权衡：保持 1.2s 节流，请求返回前用已缓存的历史结果/本地输入做即时过滤展示——手感问题用 UX 层解而非降限流阈值。若必须降，建议改指数退避（首次即时、后续递增）而非固定更低值。
- recorder：降间隔 + 指数退避组合。1.2s 防熔断（非官方 Storefront API 限流比官方更狠），但联想需 ~300-400ms 响应。建议首次请求允许较短间隔（如 350ms），触发 429 后指数退避（复用 O5 _Throttle）；同时 t12 的输入/选中同步修好后，联想稍慢用户也能先回车确认。注意与 1.3.6 已有的搜索防抖（350ms）保持节奏一致。

**结论：改进——降到 0.6-0.8s + 复用 O5 _Throttle 熔断退避；本地即时匹配兜底。**
- 3/4 明确支持降间隔（0.6-0.8s）+ 熔断退避；core-tester 主张不降间隔只加本地即时层。
- 折中点：降间隔是共识（幅度有分歧：0.35s vs 0.6-0.8s），**取保守的 0.6-0.8s**——storesearch 匿名接口无速率保障，且 core-tester 指出本机出口 IP 已被限过，直接 350ms 有熔断风险。
- 关键前提：t12 的本地即时匹配已落地（search-fixer/gui-tester 确认），熔断时本地匹配兜底，降间隔的失败代价被 UX 层吸收。
- 由 t12 落地；最终由 t20 结合 t17/t18 复测定。
